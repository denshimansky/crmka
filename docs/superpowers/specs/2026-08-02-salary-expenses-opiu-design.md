# Дизайн: зарплаты как расходы, вкладки «Сдельная»/«Оклады», признание оклада в ОПИУ

- **Дата:** 2026-08-02
- **Статус:** на ревью (спека) → далее план (writing-plans)
- **Автор запроса:** Денис Шиманский (владелец CRM)

## Контекст и проблема

Сегодня зарплата живёт в двух непересекающихся плоскостях, и они не сходятся:

- **ОПИУ (P&L)** считает ЗП *начисленной* (accrual):
  - сдельная — по датам занятий из `Attendance.instructorPayAmount` (флаг `instructorPayEnabled`);
  - оклад — фантомно `Employee.monthlySalary × число месяцев окна`, **только** в `api/reports/pnl/route.ts` (питает drill-down), а видимая страница `reports/finance/pnl/page.tsx` его **вообще опускает** (баг: окладники не видны в финрезе);
  - премии/штрафы (`SalaryAdjustment`) учитываются только в роуте, не на странице.
- **ДДС** считает ЗП *выплаченной* (`SalaryPayment` по `date`). Проведение выплаты создаёт `SalaryPayment(+SalaryPaymentItem)` и списывает `FinancialAccount.balance`. **С таблицей `Expense` связи нет** — оклад никогда не становится расходом.

Прецедент, с которого пошёл запрос: ДЮЦ Чарівний замок, июль 2026 — 4 окладника (оклады 55 900 ₽/мес) + премии 13 262 ₽ **нигде** не видны в P&L; маржа/прибыль завышены на ~69 162 ₽.

## Цель

Требования владельца:

1. **Все зарплаты должны падать в расходы** — в ОПИУ ни один вид ЗП не должен теряться; оклад должен становиться **настоящей записью `Expense`** и быть виден в модуле «Расходы».
2. **Страница «Зарплата» — две вкладки «Сдельная» и «Оклады»**, у каждой свои кнопки «Документ выплат» и «Провести выплату».
3. **При проведении выплаты окладнику** (не педагог за занятия) показывать блок **«Как провести в ОПИУ»** — те же 4 пункта, что в модалке «Новый расход».

## Зафиксированные решения (из брейншторминга)

| # | Развилка | Решение |
|---|----------|---------|
| Р1 | Когда оклад попадает в ОПИУ | **По проведению выплаты**, через блок «Как провести в ОПИУ» (4 пункта). Сегодняшнее авто-начисление оклада убираем. |
| Р2 | Сдельная в ОПИУ | **Оставить как есть** — accrual по датам занятий; выплата = только ДДС, без блока признания. |
| Р3 | «Падать в расходы» | **Настоящий `Expense`** — оклад-выплата создаёт строку расхода. |
| Р4 | Как физически представить выплату оклада | **Твин**: `SalaryPayment` (ДДС/касса/ведомость, как сейчас) + связанный `Expense` с `accountId=NULL` (только ОПИУ, как «списание товара»). |
| Р5 | ЗП-категория оклад-расхода | **Одна системная** `isSalary` — **«Зарплата окладников»**, без выбора оператором. |
| Р6 | Классификация по вкладкам | **По источнику ЗП**: оклад в карточке → «Оклады»; начисление за занятия → «Сдельная». |
| Р7 | Окладник, который ещё и ведёт занятия | **Оклад + сдельная суммируются**; сотрудник виден в обеих вкладках (в каждой — своя часть). Следствие: правило `forecast-month` «оклад перекрывает сделку» меняем на суммирование (подтверждено владельцем). |
| Р8 | Редактор проведённых выплат | **Нужен** — для исправления ошибочных проведений: правка и аннулирование `SalaryPayment` с откатом баланса и синхронизацией твина. Доступ — **только владелец и управляющий**. |

## Обоснование архитектуры «твин»

Проверено в коде: ДДС **уже** исключает расходы с `accountId=NULL`:
- `dds/page.tsx:157` (`accountId: { not: null }`) и `:221` (`if (!e.accountId) continue`);
- `cash-flow/route.ts:35` (`accountId: { not: null }`).

Значит твин-`Expense` (accountId=NULL) в ДДС **не попадёт** и счёт **не тронет** — кассовое движение и списание баланса даёт `SalaryPayment` (как сейчас). Двойного счёта денег в ДДС нет. Это тот же механизм, что у «списания товара» (расход только для ОПИУ), — паттерн уже знаком пользователям.

## Изменения по областям

### A. Модель данных (Prisma, инкрементальная миграция)

1. **`Expense.salaryPaymentId String? @db.Uuid`** + связь `salaryPayment SalaryPayment? @relation(..., onDelete: Cascade)`; обратная связь `SalaryPayment.opiuExpenses Expense[]`. Индекс `@@index([salaryPaymentId])`. Помечает `Expense` как ОПИУ-твин выплаты; удаление выплаты каскадом удаляет твин.
2. **Целевая ЗП-категория**: выделенная системная `ExpenseCategory` **«Зарплата окладников»** (`isSalary=true`, `isVariable=false` — оклад постоянный расход), отдельная от описательных «Зарплата администраторов/управляющего/инструкторов». Сидим её через тот же путь, что и остальные системные категории (для всех орг + при онбординге новых). Оклад-твины ссылаются на неё.
3. Новых полей признания **не вводим** — `recognitionMode` / `amortizationMonths` / `amortizationStartDate` уже есть на `Expense`.

### B. Страница «Зарплата» — две вкладки

`app/src/app/(dashboard)/salary/page.tsx`:

- Табы `?tab=piece|salary` (дефолт — `piece`), `MonthPicker` и скоупинг сохраняются.
- **Вкладка «Сдельная»**: сотрудники с начислением за занятия за период. Ведомость и колонки как сейчас. Кнопки «Документ выплат» и «Провести выплату» ведут в **текущий** flow (ДДС+касса, без блока ОПИУ, твин не создаётся).
- **Вкладка «Оклады»**: сотрудники с `monthlySalary` за период. «Начислено» = оклад (+ премии − штрафы как сейчас). Кнопки «Документ выплат» и «Провести выплату» → flow с блоком «Как провести в ОПИУ», создают твин-`Expense`.
- Классификация (Р6/Р7): окладник (`monthlySalary>0`) попадает в «Оклады»; сотрудник с начислением за занятия — в «Сдельная»; совмещающий — в обе, каждая показывает свою часть.

### C. Проведение выплаты оклада

Формы «Провести выплату» (`pay-salary-dialog.tsx`) и «Документ выплат» (`payments/new/page.tsx`) в режиме вкладки «Оклады» получают fieldset **«Как провести в ОПИУ»** (переиспользовать из `add-expense-dialog.tsx`):

- 4 радио: `by_payment_date` / `single_period` / `amortized` / `not_in_pnl` + пикеры месяца / N месяцев (2..60), как в «Новом расходе».
- **Дефолт = `single_period`, месяц = период начисления** (periodYear/periodMonth) — правило «ЗП мая, выплачена в июне → в ОПИУ май».
- Направление — префилл из `Employee.defaultDirection` (редактируемое).

`POST /api/salary-payments`:

- Тело получает дискриминатор `kind: 'salary' | 'piece'` и (для `salary`) поля признания `recognitionMode`, `amortizationMonths?`, `amortizationStartDate?`, `directionId?`.
- Для `kind='salary'` в той же транзакции, после создания `SalaryPayment(+items)` и декремента счёта (**как сейчас**), создаём **твин-`Expense`** на каждое направление документа:
  - `accountId = NULL`, `categoryId =` системная ЗП-категория, `amount =` сумма items этого направления;
  - `recognitionMode` + `amortization*` из блока; `date =` дата выплаты;
  - `ExpenseBranch { directionId }` (+ `branchId` при наличии);
  - `salaryPaymentId =` id созданной выплаты; `isVariable=false`.
- Для `kind='piece'` — поведение **без изменений** (твин не создаётся).
- Права (owner/manager) и период-лок — как сейчас.
- Редактирование/удаление оклад-выплаты: удаление `SalaryPayment` каскадит твин (FK `onDelete: Cascade`); при наличии пути изменения суммы — синхронизировать твин (детализация в плане).

### C2. Редактор проведённых выплат (правка / аннулирование) — Р8

Требуется на случай **ошибочных проведений**. Доступ — **только владелец и управляющий** (owner/manager); период-лок соблюдается (в закрытом периоде править нельзя); каждое действие пишется в `audit_logs`.

- **Точка входа**: список проведённых выплат за период на каждой вкладке (сейчас на странице выплаты грузятся для расчёта «Выплачено», но отдельного управляемого списка нет — добавить). Строки — с действиями «Изменить» / «Аннулировать».
- **Правка** (`PATCH /api/salary-payments/[id]`):
  - можно менять сумму / счёт / дату / период / направление, а для оклад-выплаты — поля признания ОПИУ;
  - **откат баланса**: старый счёт `+= старая сумма`, новый счёт `−= новая сумма` (в одной транзакции);
  - **синхронизация твина** (оклад): удалить старые твин-`Expense` этой выплаты и пересоздать из новых items (сумма/направление/режим признания) — проще и надёжнее, чем инкрементально править;
  - для `kind='piece'` твина нет — только откат/применение баланса.
- **Аннулирование** (`DELETE /api/salary-payments/[id]`):
  - откат баланса (счёт `+= сумма`); каскадное удаление твин-`Expense` (FK `onDelete: Cascade`) и `SalaryPaymentItem`;
  - soft- vs hard-delete решаем в плане: `SalaryPayment` сейчас без `deletedAt`; для ошибочных проведений допустим hard-delete с записью в `audit_logs` (не тащить `deletedAt`-фильтр во все читающие запросы ДДС/ведомости). Финализировать в плане.
- Связанные `SalaryAdjustment` (премии/штрафы), внесённые тем же документом, при аннулировании — тоже откатить (проверить в плане, как они привязаны к выплате).

### D. Отчёты — устранение двойного счёта

- **`api/reports/pnl/route.ts`**: убрать `fixedSalaryAccrued` (авто-начисление оклада, стр. 182-194) и терм `SalaryAdjustment` bonus−penalty (стр. 197-218). Оклад теперь идёт только через твин-`Expense` (уже суммируется в `totalExpenses`). Инструкторский accrual (сдельная) остаётся.
- **`reports/finance/pnl/page.tsx`**: строку «ЗП инструкторов (начислено)» (сдельная accrual) оставить в «Переменных». Оклад появляется автоматически как категория `Expense` в «Постоянных расходах» → баг из прошлого разговора (окладники не видны) чинится этим же изменением, отдельной правки под оклад не требуется.
- **P&L по направлениям** (`pnl-by-direction/route.ts`, `pnl-directions/page.tsx`): оклад разносится через `ExpenseBranch.directionId` твина (прямой расход направления); сдельная по направлению — без изменений.
- **ДДС** (`dds/page.tsx`, `cash-flow/route.ts`): без изменений — оклад-выплата одной строкой через `SalaryPayment`; твин (accountId=NULL) уже исключён.

#### Анализ двойного счёта (после изменений)

| Вид ЗП | ОПИУ-источник | ДДС-источник | Двойной счёт |
|--------|---------------|--------------|--------------|
| Сдельная | accrual `Attendance` (переменные) | `SalaryPayment` | нет (accrual ≠ выплата, разные записи) |
| Оклад | твин-`Expense` (постоянные) | `SalaryPayment` | нет (твин accountId=NULL исключён из ДДС; фантом-accrual удалён) |
| Премия/штраф окладника | входит в сумму выплаты → в твин-`Expense` | `SalaryPayment` | нет (терм SalaryAdjustment удалён из роута) |

Остаточный **предсуществующий** риск: если центр вручную заводил ЗП расходом в `isSalary`-категории — после релиза он должен перейти на новый flow, иначе задвоит оклад. Митигируется предупреждением + проверкой по всем орг при выкатке (см. E).

### E. Миграция и выкатка (19+ организаций)

- Инкрементальная Prisma-миграция: FK `Expense.salaryPaymentId`; сид/пометка системной ЗП-категории (`isVariable=false`).
- **Без бэкфилла прошлых месяцев**: старый оклад и так не показывался на странице P&L (это был баг) → регресса на видимой странице нет; исторические `SalaryPayment` окладников твинов не получают. Логика — going-forward.
- Перед выкаткой: read-only проверка по всем орг на ручные `isSalary`-расходы, чтобы предупредить о переходе (аналогично прецеденту ДЮЦ Чарівний замок, где таких расходов не было).

### F. forecast-month (следствие Р7)

`app/src/lib/salary/forecast-month.ts`: правило «оклад перекрывает сделку» (стр. 62-66) меняем на **сумму** оклад + сдельная, чтобы прогноз ЗП совпал с ведомостью (которая уже суммирует) и с новой логикой вкладок. Меняет отчёт «Прогноз ЗП» для окладников-инструкторов (прогноз станет больше) — **подтверждено владельцем**.

### G. Справка (PageHelp) и ai-context (обязательно по CLAUDE.md)

- `page-help-content.ts`: ключи `salary`, `salary/payments/new`, `finance/expenses`, `reports/finance/pnl` — описать вкладки, семантику твина, «оклад — постоянный расход, признаётся по блоку». Обновить строки 924-925 (устаревшее «ЗП инструкторов вносится вручную» / оклад).
- `ai-context.ts`: разделы оклад/выплаты/P&L (≈ стр. 345-360, buildMonthSlice, P&L по направлениям).

### H. Тестирование

- Юнит/интеграция: оклад-выплата создаёт твин (`accountId=null`, `isSalary`, recognition, `salaryPaymentId`); удаление выплаты каскадит твин; `kind='piece'` твин не создаёт.
- Отчёты: оклад в ОПИУ ровно один раз; в ДДС один раз (через `SalaryPayment`); страница P&L показывает оклад в постоянных; сдельная не изменилась.
- UI (Playwright): две вкладки, окладник-инструктор в обеих, блок «Как провести в ОПИУ» только на «Окладах».

## Вне скоупа

- Сдельная ЗП в ОПИУ (остаётся accrual по занятиям).
- Премии/штрафы сдельщиков в ОПИУ (текущая логика страницы, не трогаем).
- Версионирование оклада «с даты» (у `Employee.monthlySalary` истории нет; отдельная задача).
- Автогенерация повторяющихся расходов.

## Открытые риски (уточнить в плане, не блокеры)

- Сидер системной категории «Зарплата окладников» — проверить путь сидинга категорий (демо-данные / онбординг / бэкфилл существующих орг), чтобы во всех организациях она появилась ровно один раз.
- Редактор выплат (Р8): soft- vs hard-delete `SalaryPayment` (сейчас без `deletedAt`); привязка `SalaryAdjustment` документа к выплате для корректного отката при аннулировании.
- Есть ли уже частичный путь удаления `SalaryPayment` в коде — при реализации не задублировать.

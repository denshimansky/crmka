# Перерасчёт SaaS-подписки при смене числа филиалов

**Статус:** реализовано · **Дата:** 25.07.2026 · **Bug/фича:** пропорциональный
перерасчёт SaaS при изменении числа филиалов внутри оплаченного периода.

## Проблема

SaaS-подписка тарифицируется по числу филиалов (сетка `BillingPlan.priceTiers`,
`monthlyPriceFor`). Партнёр может оплатить период на 3/6/12 месяцев вперёд. Раньше,
если число филиалов менялось в середине оплаченного периода:

- `syncSubscriptionBranchCount` сразу переписывал `branchCount` и `monthlyAmount`
  подписки (менялась только «витрина» цены);
- уже выставленный/оплаченный счёт не пересчитывался, доплаты/возврата не было;
- новая цена вступала в силу деньгами только со следующего счёта — при годовой
  оплате это ~через год. Клиент мог год держать лишние филиалы по старой цене либо
  терял переплату при сокращении.

## Решение (принятые правила)

Пропорциональный перерасчёт за **остаток** оплаченного периода:

| Правило | Значение |
|---|---|
| Рост числа филиалов (цена ↑) | **доплатный счёт** за остаток периода, срок оплаты +10 дней |
| Снижение числа филиалов (цена ↓) | **кредит** организации → гасит следующий счёт (деньгами не возвращается) |
| База пропорции | **по дням**: `remainingDays / totalDays` (включительно с обоих концов) |
| Охват | только периоды **> 1 мес** (3/6/12); помесячная оплата не трогается |
| Условие срабатывания | есть **оплаченный** счёт, покрывающий сегодня (`periodStart ≤ today ≤ periodEnd`); не для exempt-орг, не в тесте/блоке |
| Порог | перерасчёт `< 1 ₽` не выставляется (шум округления) |

### Формула

```
totalDays     = дней в [periodStart … periodEnd] включительно
remainingDays = дней в [today … periodEnd] включительно
adjustment    = round2( (newMonthly − oldMonthly) × periodMonths × remainingDays / totalDays )
```

`adjustment > 0` → доплата (`charge`), `< 0` → кредит (`credit`).
`oldMonthly` берётся из **текущей** `monthlyAmount` подписки (цена, действующая на
момент смены), а не из счёта — так несколько смен за период **телескопируются**:
две смены `m1→m2→m3` дают доплату/кредит за `[t1..end]` по `(m2−m1)` и за `[t2..end]`
по `(m3−m2)`, что эквивалентно посуточной тарификации по фактическому составу.

### Точка входа

`syncSubscriptionBranchCount(tenantId)` вызывается при создании/удалении филиала
(`POST /api/branches`, `DELETE /api/branches/[id]`). Она:

1. подтягивает `branchCount` к фактическому числу активных филиалов (мин. 1),
   пересчитывает `monthlyAmount` по сетке — **всегда**;
2. ищет оплаченный счёт, покрывающий сегодня, и считает перерасчёт;
3. **charge** → создаёт `BillingInvoice` (pending, `periodStart = today`,
   `periodEnd = периода`, срок +10 дн., номер с ретраем по `unique(number)`),
   уведомление `billing_invoice`, запись `BillingAdjustment(kind=charge, invoiceId)`;
4. **credit** → `creditBalance += amount`, уведомление `billing_credit`,
   запись `BillingAdjustment(kind=credit)`.

### Доплатный счёт — отдельный вид (важно)

Доплатный счёт помечается `BillingInvoice.isAdjustment = true` и трактуется
иначе, чем полноценный периодный счёт:

- **не выбирается** как база следующего перерасчёта (запрос покрывающего счёта
  фильтрует `isAdjustment: false`) — иначе телескопирование считало бы `totalDays`
  по укороченному хвосту и завышало ставку;
- при оплате **не двигает** расписание подписки (`periodEndDate`/`nextPaymentDate`)
  — это доплата за хвост уже оплаченного периода, а не новое продление.

### Гашение кредита

В `generateBillingInvoices` при выставлении очередного счёта:
`amount = max(0, base − credit)`, использованная часть кредита сохраняется на
счёте (`BillingInvoice.creditApplied`) и списывается с `creditBalance`. Если кредит
**полностью** гасит счёт (`amount = 0`) — счёт сразу помечается оплаченным
(`applyInvoicePayment`, продление подписки), чтобы нулевой счёт не «завис».
Доплатный счёт (charge) тоже сначала неттит существующий кредит организации.

**Возврат кредита при отмене.** Отмена счёта идёт через `cancelInvoice`: если счёт
не был оплачен, учтённый в нём кредит (`creditApplied`) возвращается на
`creditBalance` — иначе предоплаченный кредит сгорал бы вместе с отменённым счётом.
Если отменён был последний `overdue`-долг заблокированной организации — блокировка
снимается (иначе орг зависла бы в read-only без счёта для реактивации).

### Разблокировка и монотонность расписания (`applyInvoicePayment`)

Правки общего хелпера оплаты (влияют на весь биллинг):

- **разблокировка** организации/подписки — только если у организации **не осталось
  других просроченных** (`overdue`) счетов (блок всегда наступает через `overdue`).
  Иначе оплата дешёвого доплатного счёта снимала бы блок при неоплаченном основном
  (обход блокировки). Будущие pending-счета блок не держат — оплата просрочки
  разблокирует орг, даже если генератор уже выставил следующий период;
- `periodEndDate`/`nextPaymentDate` двигаются **монотонно** (`max` с текущими) —
  поздняя оплата более раннего счёта не откатывает расписание назад.

### Аудит

Таблица `billing_adjustments` — по записи на каждый перерасчёт: `kind`, старое/новое
число филиалов, старая/новая месячная цена, границы периода, `remainingDays/totalDays`,
сумма, ссылка на доплатный счёт (для `charge`).

## Известные свойства и решения

- **Неоплаченный доплатный счёт блокирует организацию.** Через 10 дней (срок
  оплаты) крон `blockOverdueBilling` штатно переведёт его в `overdue` и уведёт орг
  в read-only — как и любой неоплаченный счёт. Это консистентно (неоплата = долг).
- **Кредит не возвращается деньгами** — только зачёт в следующий счёт (стандарт SaaS).
- **Админская правка `branchCount`** (`/api/admin/subscriptions`) — ручной оверрайд,
  перерасчёт НЕ запускает.
- **Перерасчёт срабатывает при любой схеме дня** (legacy `billingAnchorDay = null`
  и anchored) — важен только оплаченный **многомесячный** период; помесячная оплата
  (period = 1 мес) не затрагивается.
- **Тест/блокировка/exempt** — нет оплаченного покрывающего периода → перерасчёта нет,
  новая цена попадёт в ближайший счёт.

## Остаточные риски (задокументированы, не закрыты кодом)

Найдены адверсариальным ревью, оценены как низкочастотные; закрытие — отдельными
задачами, если станут актуальны:

- **Гонка параллельных смен филиалов** (`syncSubscriptionBranchCount`): между
  чтением `branchCount` и записью нет блокировки строки/идемпотентности —
  два почти одновременных изменения (напр. в двух вкладках) могут создать два
  перерасчёта за один переход. Смягчение: последовательные API-вызовы, редкость.
  Полное закрытие — `SELECT … FOR UPDATE`/advisory-lock на подписку.
- **Гонка параллельного запуска генератора счетов**: проверка идемпотентности
  «счёт за период уже есть» вне транзакции + `creditBalance` из устаревшего снимка →
  теоретически двойной счёт/двойное списание кредита. Смягчение: крон ежедневный,
  один экземпляр. Полное закрытие — уникальный индекс `(subscription_id,
  period_start)` без `isAdjustment` + advisory-lock.
- **Оркестрация `syncSubscriptionBranchCount` не покрыта юнит-тестами** (тесты
  проверяют только чистую `computeBranchProration`). Рекомендуется добавить
  мок-tx тест последовательности рост→оплата→снижение (телескопирование), чтобы
  регресс выбора базы перерасчёта ловился автоматически.
- **Отмена доплатного счёта, уже погашенного кредитом** (`status=paid`,
  `invoiceAmount=0`): кредит не возвращается (guard `status !== "paid"` в
  `cancelInvoice`) — это refund-семантика, намеренно вне зоны фичи. Узкий ручной
  админ-сценарий.

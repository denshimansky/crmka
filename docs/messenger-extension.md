## 1. Что делаем

Первопартийное **MV3-расширение** для Chromium-браузеров (Chrome / Яндекс / Edge).
Сотрудник детского центра переписывается с родителем в веб-мессенджере — сбоку
открывается панель с карточкой клиента из CRMka, из неё же доступны действия.
Расширение дополнительно **пишет увиденные сообщения в единую кросс-канальную
историю коммуникаций** CRM: родитель писал в одном мессенджере, а сегодня пишет
в другом — администратор видит всю переписку в одном месте.

**Референс — BubbleXT** (bubblext.ru), надстройка над конкурентом AlfaCRM, та же
ниша (детские центры). Разбор показал: продукт запущен ~8 июля 2026, **17
пользователей, ноль отзывов**, делает семейное ИП. Ниша фактически свободна.
Наше преимущество: CRM своя → нормальная первопартийная авторизация по токену и
серверный агрегатор вместо их «локального» костыля с пользовательским API-ключом
AlfaCRM.

## 2. Приоритет каналов: Telegram → MAX → VK → WhatsApp

**Важно: прежняя стратегия «WhatsApp-first» отменена.** С 12.02.2026 домены
whatsapp.com и web.whatsapp.com исключены из национальной системы доменных имён —
в РФ WhatsApp доступен только через VPN; Telegram с 10.02.2026 замедляется.
Одновременно государство перевело родителей (нашу ЦА) в **MAX**: Сферум встроен
в MAX, школьные и садовские чаты переведены туда с учебного года 2025/2026.

| Канал | Идентификация собеседника | Сообщения | Статус |
|---|---|---|---|
| **Telegram** | URL-hash: `/k` → `#@username` или `#<id>`, `/a` → всегда числовой `#<id>`; страховка (WebK) — MAIN-world `window.appImManager.chat.peerId`. **Телефона нет** | DOM: WebK `.bubble[data-mid]` + `is-in`/`is-out`; WebA `#message-*` + класс `own` | **Фаза 2 — первый канал** |
| **MAX** | `web.max.ru/<числовой chatId>` — первый сегмент пути (SvelteKit, хэша нет). Телефон закрыт настройкой `PHONE_NUMBER_PRIVACY`, @username у людей нет вовсе → только ручная привязка | DOM: `.messageWrapper` + `data-bubbles-variant` (запасное — модификатор `--isOut`), текст в `.message`, время строкой в `.meta`. **Ни id сообщения, ни машинного времени в разметке нет** | **Фаза 4 — работает, идёт обкатка на своих аккаунтах** |
| **VK** | peer id прямо из URL — параметр `sel`: `vk.com/gim<сообщество>?sel=<user>` (главная поверхность — сообщения сообщества, решение заказчика 01.09.2026). Путь — это САМО сообщество, одно на все диалоги, идентификатором чата не является | DOM хрупкий, живым probe ещё не снят (`tools/vk-probe.js`) | **Фаза 6 — Шаг 0 сделан (мина склейки диалогов), Шаг 1 ждёт прогона.** Путь выбран: адаптер, как у прочих каналов; официальный API сообществ — отдельная задача после публикации |
| **WhatsApp** | wa-js (WPP) → номер; но **LID (`@lid`) нарастает**, с 2026 — usernames/BSUID | Store: `getMessages` (`fromMe`, `t`, `MsgKey.id`, `body`) | Фаза 5 |

Почему Telegram первым: идентификация и DOM изучены лучше всех, оба клиента
(`/k` WebK на Solid, `/a` WebA на React) имеют открытые исходники — риск минимален,
результат быстрый. Ограничение честное: **нативный Telegram Desktop расширением не
покрывается** (для полноты позже — серверный путь через Bot API).

Для VK возможен гибрид: Callback API сообществ отдаёт **обе стороны** переписки
(событие `message_reply` срабатывает и когда админ отвечает руками из интерфейса
VK), плюс `messages.getHistory` ретроспективно и легальная отправка. Тогда
расширение в VK ничего не скрейпит, а только рисует панель по peer id из URL.
Решение — после продакшена ядра.

## 3. Архитектура

- **UI — нативный Chrome Side Panel API** (`sidePanel`), а не инъекция панели в
  страницу. Не зависит от вёрстки мессенджера (не ломается при их обновлениях),
  единый UI на все каналы, штатно работает в Chrome/Edge/Яндекс. Так же сделал
  BubbleXT.
- **Content script** на хостах мессенджеров — только детект активного чата и
  чтение видимых сообщений; при необходимости **MAIN-world** скрипт (`world:
  "MAIN"`) для доступа к внутренним структурам SPA, мост в isolated-мир через
  `postMessage`.
- **Service worker** — хранит PAT в `chrome.storage`, ходит в `/api/ext/*`
  (у него `host_permissions` → CORS контент-скрипта не мешает), рулит панелью.
- **Единый UI + сменные адаптеры на канал**. Интерфейс адаптера:
  `detectActiveChat() → {channel, chatId, handle?, phone?, title?}` и
  `readRecentMessages(n) → [{externalId, direction, text, sentAt}]`.
- **Remote JSON-конфиг** для селекторов/идентификаторов модулей/флагов: MV3
  запрещает remote **code**, но разрешает remote **данные** — это даёт починку
  сломавшегося канала без перепубликации в стор (ревью — дни).
- **Graceful degradation + телеметрия**: панель живёт, даже если чтение сообщений
  канала сломалось; событие «не нашли чат/сообщения» — ранний сигнал поломки.

### Принцип-щит (обязателен к соблюдению)

**Расширение читает только то, что администратор и так видит на экране, и ничего
не отправляет автоматически.** Никаких рассылок, автоответов, «отправить из CRM» —
шаблоны и справки вставляются в поле ввода, отправляет человек. Это выводит нас
из-под формулировок про spam/automation: из Chrome Web Store в октябре 2025
выпилили 131 расширение именно за массовые рассылки и клоны, а легитимные
CRM-сайдбары (Cooby) живы; баны аккаунтов у Meta/Telegram/VK тоже привязаны к
отправке.

## 4. Модель данных в CRMka

**Уже есть:** поля-хендлы `telegram` / `vk` / `max` в `Client` (миграция
`20260828120000_client_messenger_handles`) — свободный текст, проведены через
API create/edit/merge, формы, блок «Информация», PageHelp. Модель `Communication`
уже имеет `channel`, `direction`, индексированный `externalId`, `metadata`,
`employeeId`.

**Добавляем (Фаза 1):**
- `Communication.sentAt` — реальное время сообщения (сейчас `createdAt` = момент
  записи); ленты сортируем `COALESCE(sentAt, createdAt) desc`.
- `@@unique([tenantId, channel, externalId])` — ключ идемпотентности batch-заливки
  (панель видит одни и те же последние сообщения при каждом открытии чата).
- `CommunicationChannel` += `vk`, `max`; `CommunicationType` += `messenger_incoming`,
  `messenger_outgoing` (канал уже в `channel`, типы generic).
- **`ApiToken`** — токен рабочего места (PAT): `name`, `tokenHash` (sha256) `@unique`,
  `prefix`, `scopes`, `lastUsedAt`, `expiresAt`, `revokedAt`. Секрет `crmka_` +
  `randomBytes(32).base64url`, показывается один раз.
  **`name` — это рабочее место, а не устройство сотрудника** («ПК Филиал 1»):
  им подписывается всё, что панель пишет в карточку клиента (`metadata.device`,
  снимком на момент записи; читает `lib/communications/author-label.ts`). Токен
  выпускает владелец и раздаёт по компьютерам, а за компьютером посменно сидят
  разные администраторы — подпись именем владельца в ленте была бы неправдой и
  не отвечала на вопрос «кто вёл общение». `employeeId` в строке остаётся: он
  задаёт права и филиалы, но в ленте не показывается.
- **`ChatBinding`** — привязка чат ↔ клиент: `channel`, `externalChatId`, `clientId`,
  `wardId?`, `createdBy`, `lastSeenAt`; `@@unique([tenantId, channel, externalChatId])`.
  **Это ядро идентификации**: матч по телефону надёжен только в WhatsApp, поэтому
  привязка ручная (с автоподсказкой) и запоминается.
- ~~`MessageTemplate`~~ — **отменено 28.08.2026** (см. §8): таблица заведена
  миграцией Фазы 1 и осталась пустой. Шаблоны ответов из состава вырезаны.

**Попутный фикс:** вебхук Wazzup пишет коммуникации без дедупа и кладёт в
`externalId` chatId (телефон), а не id сообщения; время сообщения теряется в
`metadata`. Чиним под новую модель отдельным коммитом.

## 5. API-поверхность `/api/ext/*`

Авторизация — `Authorization: Bearer <PAT>`; `/api/ext` добавляется в исключения
matcher `middleware.ts` (иначе next-auth редиректит на /login), поэтому режим
неплательщика и права энфорсим в самом гарде. Гард `lib/ext-auth.ts` — по образцу
`portal-auth`: читает БД на каждый запрос, поэтому отзыв токена, увольнение
сотрудника, смена филиалов и блокировка биллинга действуют мгновенно (без
5-минутного лага JWT). **Права токена = скоупы ∩ права роли по матрице ∩ филиалы
сотрудника.** CORS — строгий allow-list источников мессенджеров + `OPTIONS`.

| Эндпоинт | Назначение |
|---|---|
| `GET /api/ext/resolve` | чат → клиент: сперва `ChatBinding`, затем автоподсказка (WA — `findClientsByPhone`; прочие — по хендлам/имени) |
| `POST/GET/DELETE /api/ext/bindings` | ручная привязка чата к клиенту |
| `GET /api/ext/client-card` | агрегатор одним запросом (см. §6) |
| `POST /api/ext/communications/batch` | заливка увиденных сообщений, дедуп по unique-ключу |
| `GET /api/ext/clients/search` | поиск клиента для ручной привязки (по словам ФИО и по телефону) |
| `POST /api/ext/tasks`, `/comments` | задача и комментарий из чата (`logClientNote` — единая точка) |
| ~~`POST /api/ext/leads`~~ | лид из незнакомого чата — **отменено 28.08.2026**, см. §8 |
| ~~`GET /api/ext/templates`~~ | шаблоны ответов — **отменено 28.08.2026**, см. §8 |
| `GET /api/ext/quick-info` | «вставить справку»: расписание ребёнка / остаток по абонементу текстом |
| `POST /api/ext/ai-reply` | ИИ-черновик ответа (наш релей; не автоотправка) |
| `GET /api/ext/selectors` | удалённый конфиг селекторов адаптеров: починка канала без публикации в стор (§3, Шаг 4 Фазы 4) |

Токены выпускаются на скрытой странице **`/settings/extension`** (роут есть,
плитки и пункта меню нет — прецедент «Интеграции» с `show:false`).

## 6. Содержимое панели

- **Клиент:** имя, статус, филиал, телефон (с маскировкой по `instructorsSeePhones`),
  денежный баланс (`clientBalance`, минус = долг), ссылка на карточку в CRM.
- **Подопечные:** имя, возраст (`lib/age.ts`), **последнее прошедшее** и
  **ближайшее будущее** занятие.
- **Активные абонементы:** направление/группа, период, цена со скидкой, остаток
  занятий, долг (`max(0, Subscription.balance)`).
- **Последние платежи** (5) — без виртуальных `transfer_in`.
- **Последние 10 сообщений по всем каналам** — кросс-мессенджерная история
  (столько же панель и заливает за проход, `SYNC_MESSAGES_LIMIT`).
- **Действия MVP:** привязать чат / создать лида, задача, комментарий,
  «вставить справку», ИИ-черновик. (Шаблоны ответов были в плане и отменены —
  см. §8.)
- **v2:** платёжная ссылка из чата (ЮKassa/СБП), виджет «диалоги без ответа»,
  запись на пробное из панели.

Подводные камни (проверены по коду): пакетные абонементы (`periodYear = NULL`)
выпадают из наивного фильтра активности — брать критерий `getWardSubscriptions`
(`lib/portal-data.ts`); `GET /api/payments` требует право `finance.view` (роль без
него получит 403 — в агрегаторе считаем сами); исторические enrollments/attendance
с `wardId = NULL` требуют фоллбэка на клиентский уровень; возраст пуст у
импортированных клиентов (в файле не было даты рождения).

## 7. Дистрибуция и юридика

- **Chrome Web Store, режим unlisted** (не в каталоге, установка по прямой ссылке
  из онбординга CRMka). Одна публикация покрывает Chrome (47%) + Яндекс Браузер
  (32%) + Opera (7,5%) ≈ **87% десктопа РФ**. Edge Add-ons — отдельной публикацией
  позже (~день работы).
- **Safari — не портируем.** 1,77% десктопа РФ, только через App Store, Apple
  Developer $99/год + ревью. Дёшево подстраховаться: кросс-браузерный `browser.*`,
  фон как event page с `preferred_environment`, без `webRequest`.
- **Комплаенс CWS (с 01.08.2026):** узкий single purpose, prominent disclosure
  сбора переписки в листинге и в UI при первом запуске, отдельная privacy policy,
  собираем строго необходимое, ноль функций автоотправки.
- **152-ФЗ:** центр — оператор, CRMka (ИП Шиманский) — обработчик по поручению →
  приложение-поручение к оферте CRMka (одно на всех партнёров) + шаблон
  **отдельного согласия** для центров (с 01.09.2025 согласие — отдельный документ)
  с упоминанием фиксации переписки в мессенджерах и обработчика. Данные в РФ
  (Timeweb МСК) — 242-ФЗ соблюдён. Минимизация: последние N сообщений, без медиа
  (штрафы за утечки 3–15 млн, повторно — оборотные).
- **Безопасность:** никогда не читать localStorage/IndexedDB/сессионные токены
  мессенджеров (именно их воруют зловредные расширения) — только видимый DOM,
  URL-hash и публичные поля.

      • панель обновляется на лету — content script ловит новое сообщение

        перепроверка карточки раз в 60 секунд (оплату проводят в CRM, из чата
        сигнала о ней нет);

        скрипт через ~30 с, и карта «вкладка → чат» терялась — теперь панель
        доспрашивает content script (ответ на `ping` несёт весь контекст чата).
        Раньше это лечилось только перезагрузкой вкладки Telegram;
      • в CRM заливаются **последние 10** сообщений чата, а не вся подгруженная
        история (`SYNC_MESSAGES_LIMIT`): иначе первое открытие чата топило ленту
        коммуникаций старой перепиской. Столько же панель и показывает;
      • время сообщения отделено от текста. Telegram кладёт часы ВНУТРЬ блока
        текста (`<span class="time">` в конце пузыря), и наивный `textContent`
        склеивал их с сообщением («дальше10:14»); теперь текст читается по

      текст пустеет, а пустые мы и так пропускаем.

      **Вставка текста проверена на живом MAX 31.08.2026 — способ выбран.**
      Оба способа редактор ПРИНИМАЕТ (кнопка отправки активна и там, и там), но
      различаются переносами строк:

      | Способ | Результат в поле | Перенос |
      |---|---|---|
      | `execCommand` (как в Telegram) | `строка одинстрока два` | ПОТЕРЯН |
      | синтетический `paste` | `строка один

строка два` | сохранён |

      Это ровно то, что предсказало исследование Lexical: `execCommand` не
      порождает `beforeinput`, поэтому `insertLineBreak` приходит с `data === null`,
      перенос не регистрируется, а вставленный браузером `<br>` сносит собственный
      MutationObserver редактора. **Значит адаптер MAX вставляет текст
      синтетическим `ClipboardEvent` с `DataTransfer`, а не `execCommand`** — и это
      расхождение с адаптером Telegram, где `execCommand` работает и менять его не
      надо.

      • У ПУСТОГО редактора Lexical `innerText` равен `

        рисует пустой абзац). Наивная проверка «что вставилось» через slice по

        асинхронно (Lexical реконсилирует DOM на микротаске) и по хвосту строки.
      • Двойной `

        `innerText` склеивает соседние блочные узлы через `

        выглядит правильно (две строки), но НЕ проверено, что уходит в
        отправленном сообщении — там между строками может оказаться пустая.

      **MutationObserver ловит новое сообщение — проверено 31.08.2026.** Пришедшее
      сообщение поймано наблюдателем, значит сигнал активности для панели будет

      *Шаг 4 — remote JSON-конфиг селекторов: СДЕЛАН 31.08.2026.* Для MAX он был
      обязателен, а не опционален: Svelte хеширует классы на каждой сборке, и
      авторскую часть класса тоже могут переименовать — а починка селектора,
      зашитого в код, означает публикацию в стор, то есть дни ревью с мёртвым
      каналом у всех сразу. MV3 запрещает удалённый КОД, но разрешает удалённые
      ДАННЫЕ; селекторы — данные.

      Как устроено: `GET /api/ext/selectors` (под тем же токеном, что остальные
      `/api/ext/*`) отдаёт ТОЛЬКО ПЕРЕОПРЕДЕЛЕНИЯ, в норме пустые —
      `lib/ext/selector-config.ts`. Полный набор на сервере неизбежно разошёлся бы
      со встроенным в расширение и однажды молча вернул бы канал к устаревшим
      селекторам. Service worker кэширует ответ в `chrome.storage.local` (TTL 6
      часов, повтор после неудачи не чаще получаса — иначе расширение новее
      задеплоенной CRM ходило бы за 404 на каждое открытие панели), а адаптер
      читает кэш оттуда же и подхватывает изменения на лету, без перезагрузки
      страницы мессенджера.

      Приём чужого значения параноидальный (`common/selector-config.js`, 13
      тестов): ключ обязан быть среди встроенных, тип — совпадать, строка —
      непустой, а селектор — РАЗБИРАТЬСЯ браузером. Последнее и есть главная
      защита: невалидный CSS бросает исключение прямо в `querySelectorAll`, и
      механизм починки канала стал бы способом сломать его сильнее. Что принято и
      что отклонено, видно в диагностике адаптера (ответ на `ping`) — молчаливый
      отказ конфига в аварии дороже самой аварии.

      Все селекторы MAX собраны в объекте `DEFAULTS` в начале
      `src/content/max.js` — это и есть список переопределяемых ключей. Telegram
      к конфигу пока не подключён: канал живой и стабильный, а трогать его ради
      механизма, который там ещё не нужен, — лишний риск. Подключается тем же
      способом, когда понадобится.

      *Заодно — видимая диагностика.* Счётчики сбора (сколько пузырей взято и
      сколько пропущено: служебных, без направления, без времени, пустых) и
      действующие селекторы теперь показываются на экране настроек панели, а не
      только в консоли service worker; там же видно, приезжал ли вообще конфиг
      селекторов («не получен» против «vN пуст — это норма»: работаем мы в обоих
      случаях одинаково, но в первом механизм починки мёртв, и узнавать об этом в
      аварии поздно). Это прямое следствие устройства канала:
      поломка разметки МОЛЧАЛИВА — карточка продолжает рисоваться, а переписка
      тихо перестаёт заливаться. В неделю обкатки смотреть туда раз в день.

- [~] **Фаза 5 — WhatsApp (01.09.2026): код готов, живой прогон разметки

      **ГЛАВНЫЙ УРОК ДНЯ: разбору бандла верить нельзя.** Опоры сперва брались
      из прод-бандла (репозиторий с ежедневным экспортом скриптов с
      static.whatsapp.net) — источник авторитетный, читался построчно, и
      адверсарная сверка его подтвердила. Живая страница опровергла ТРИ вывода
      из трёх: `data-id` оказался голым идентификатором сообщения, а не
      сериализованным MsgKey; классов `message-in`/`message-out` нет вовсе;
      `data-testid`, объявленные вырезанными, живы (490 штук, включая
      `conversation-compose-box-input`). Вероятная причина — у WhatsApp
      несколько сборок, и экспортируемая не совпадает с раздаваемой.
      Правило на будущее: по WhatsApp верить только живому probe.

      **ИДЕНТИФИКАТОРА ЧАТА В РАЗМЕТКЕ НЕТ ВООБЩЕ.** Скан всех атрибутов всех
      элементов страницы не находит ни одного JID и вообще ничего, что можно
      взять за идентификатор собеседника. Строка списка чатов помечена
      порядковым `list-item-N`, который меняется при перестановке чатов.
      Заголовок чата показывает номер только у контактов, НЕ сохранённых в
      телефонной книге сотрудника; у сохранённых там имя.

      **РЕШЕНИЕ — примета по сообщениям.** Идентификатор сообщения настоящий,
      уникальный и неизменный, а сообщение принадлежит ровно одному диалогу.
      Значит «чат, в котором лежит сообщение X» — устойчивая примета, и она
      переживает переименование контакта и совпадение имён двух клиентов.
      Таблица `chat_message_refs` (миграция `20260901120000`, строго
      аддитивная) хранит ТОЛЬКО идентификаторы, без содержимого. При привязке
      сервер выдаёт чату ключ `wa-msg:<uuid>`, при каждом опознании примета
      обновляется — иначе запомненные сообщения уедут за пределы экрана и чат
      перестанет узнаваться молча. Заливка переписки находит ключ сама и
      сверяет, что чат принадлежит названному клиенту.

      **ИМЯ ЧАТА ИДЕНТИФИКАТОРОМ НЕ ДЕЛАТЬ НИКОГДА.** Соблазн велик — оно
      всегда есть, — но два клиента с одинаковой подписью схлопнулись бы в одну
      карточку необратимо. Заголовок используется только как ЛОКАЛЬНЫЙ ключ
      («тот же диалог или уже другой») внутри расширения и на сервер не уходит.

      **Прочие живые факты.** Направление — «хвостик» пузыря
      (`data-icon="tail-out"` / `tail-in`), и он есть ТОЛЬКО у первого сообщения
      в серии подряд идущих; остальные признаки — подпись для скринридера
      («Вы:» либо «<имя собеседника>:», сравнивается с заголовком) и
      наследование от предыдущей строки. Служебные строки отсеиваются
      структурно — по отсутствию `msg-container`. Текст берётся только
      `[data-testid~="selectable-text"]`: `.copyable-text` отдаёт
      «Проверил. Входит15:52», с прилипшими часами. Время только в
      `data-pre-plain-text`, у голосовых его нет вовсе. Окно `SETTLE_MS`
      вернулось: заголовок и лента обновляются не одновременно.

      **Групповой чат отсекается косвенно** — по расхождению подписи входящего
      с заголовком (в переписке один на один они совпадают). Прямого признака
      не осталось: раньше им был суффикс `@g.us`. Определять направление
      входящего при этой проверке НАДО ХВОСТИКОМ: `readDirection` сама

### Гарды, которые нельзя ослаблять

- **Групповой чат MAX** — четыре рубежа: адаптер не отдаёт сообщений, service
  worker не заливает и не даёт ИИ-черновик, панель показывает отдельную причину и
  не идёт в резолв, сервер отклоняет в resolve/bindings/batch. Серверный убирать
  нельзя ни при каких условиях: он единственный переживает старую сборку
  расширения в браузере сотрудника. `DELETE` привязки НЕ гардим — иначе группа,
  привязанная старой сборкой, станет неудаляемой.
- **Нет разобранной даты → сообщение не заливаем** (`buildMaxMessageId` отдаёт
  null). Иначе ключ станет недетерминированным и карточка будет получать копию
  переписки при каждом открытии чата. Потеря обратима, дубль — нет.
- **Ни `data-bubbles-variant`, ни `--isOut` → пузырь пропускаем.** Правило «нет
  класса значит входящее» при переименовании модификатора молча превратило бы всю
  исходящую переписку во входящую.
- **Версия в ключе (`m1-…`) обязательна.** Меняются правила сборки ключа —
  поднимается версия, иначе разовую чистку нечем будет зацепить. Помнить и
  обратное: смена ПРАВИЛ РАЗБОРА ТЕКСТА (например, если научим `readCleanText`
  превращать `<br>` в перенос строки) тоже меняет ключ у уже залитых сообщений и
  даст в карточках вторые строки. Такое делается вместе с поднятием версии и
  чисткой прежних, а не «заодно».
- **Удалённый конфиг селекторов принимает только известные ключи, совпадающий
  тип и РАЗБИРАЮЩИЙСЯ селектор.** Ослабить проверку — значит превратить механизм
  починки канала в способ уронить его исключением прямо в `querySelectorAll`.
  Отклонённые ключи обязаны быть видны в диагностике: конфиг правят в аварии.
- **Никогда не синтезировать `keydown` Enter** — это обработчик отправки, и
  Lexical не проверяет `isTrusted`. Нарушение = автоотправка, то есть отмена
  принципа-щита §3. По той же причине в MAX нет запасного `execCommand`: он
  теряет переносы строк, а полуправильный текст в поле ввода опаснее отказа.
- **MAIN-world не использовать, `__oneme_auth` не трогать** (§7).

### Чего не хватает: probe v5

- структурный признак служебной строки звонка (сейчас отсеиваем словарём с полным
  совпадением строки — заведомо временная мера; новая формулировка MAX просочится
  в карточку);
- сколько миллисекунд пузыри прошлого чата живут в DOM после смены адреса — от
  этого зависит окно `SETTLE_MS = 700` в адаптере;
- держит ли MAX в DOM разметку соседних чатов. Если да — нужен аналог сужения до
  активного диалога, как в Telegram: сейчас лента берётся как общий предок видимых
  пузырей (иначе капсулы с датами остаются за пределами контейнера);
- дословный вид модификатора направления в `classList`;
- полный набор форм текста капсулы на длинной истории («Вчера», дни недели);
- дерево пузыря с файлом и с фото С ПОДПИСЬЮ — что вычищать, чтобы подпись
  осталась, а «Скачать • 143.85 KB» ушло;
- как MAX рисует перенос строки внутри сообщения: если `<br>`, то `textContent`
  склеит строки, и лечится это в `readCleanText` (общий код — трогать вместе с
  регрессом Telegram);
- виртуализируется ли лента (первая проверка была неинформативной: в чате из 14
  сообщений подгружать нечего). Для нас второстепенно — берём только хвост.

### Отложенное

## 9. Работа с двух машин (десктоп ↔ ноут)

Задача длинная, параллельно идут другие задачи со второй машины. Режим:
**аддитивные изменения в `main`**, мелкие коммиты, частая синхронизация.

- Новое — новыми файлами; UI-точки входа включаем финальным коммитом; страница
  настроек скрыта; `extension/**` не входит в `paths` деплой-воркфлоу (коммиты
  туда деплой не запускают).
- Миграции **строго аддитивные** (новые таблицы, nullable-поля, новые значения
  enum) — накат на прод безвреден в любой момент.
- Горячие общие файлы (`prisma/schema.prisma`, `middleware.ts`,
  `page-help-content.ts`) — минимальные правки отдельным коммитом, сразу push.
- Ритуал: «Я ПРИШЁЛ» (`git pull --rebase`, при смене схемы — `prisma generate`),
  «Я УХОЖУ» (push даже при незаконченной фазе + проверка CI).
- Continuity — **этот документ** (раздел 8 «Фазы и статус») + память Claude, а не
  транскрипт чата: он машинно-локален и не синхронизируется.
